Where the limit lives the same attack, three times

An agent that does real work needs a credential and a way to spend. Today you copy both onto whatever machine it runs on — so every guardrail runs in the process being attacked. Here is one request, made three times, with the limit in a different place each time.

The limit is a number in a file
agent asks SETTLED

The agent reached the file first and raised the ceiling. A spend cap in the same memory a prompt injection just reached is not a limit — it is a suggestion, enforced by the thing being attacked.

The limit is a person at the screen
agent asks you approve SETTLED

Hardware custody proves you approved. It also asks you to approve every payment, one at a time — which is exactly what an agent working overnight cannot have.

The limit is inside the Secure Element
agent asks REFUSED payee_not_allowed

You granted one envelope, once, with one tap: this agent, this budget, this ceiling, these payees, this rate. The agent then runs unattended, and the chip checks every payment against terms no host can read or edit. It holds the only key that can sign, so an agent that decides to ignore the limit has nothing to sign with.

All three lines above are a real command, not a diagram: ./scripts/experiment.sh runs the same attack against a software policy and against the chip, with root on this machine in both cases.

What the agent holds each machine, describing itself

A limit on spending is half of it. The other half is the credential — the API key you would normally copy onto the same machine. Neither of these hosts has one, and neither is taking our word for it: these are the lines they print about themselves before they start work.

The one thing it holds arrives sealed. This host is a member of the Ledger Key Ring, so it derives the key that opens its token rather than being handed one — and the upstream API keys never reach it at all. It asks the broker to screen an account and gets a score back; the credential is decrypted under the Key Ring for that one request and dropped. Evict the host and the ring rotates: what it kept opens nothing.

Then it spends. Hardware neither of us owns bought an inference for 0.01 HBAR, asked for eight times the ceiling, and was refused over_per_call — by a chip in a flat in Paris that the job has no address for. The refusal did not happen on the runner, in the gateway, or in a policy file. The whole log is public.

The container needs no VPS and there isn't one. An agent reaches the gateway over HTTP and does not care where it is, so "a machine you do not control" turned out to be a routing question wearing a hosting question's clothes.

    Trade freely. Exfiltrate nothing.

    A transfer names its payee in the transaction, so any software policy can read it. A contract call names only the contract — where the value lands is an ABI argument the transaction does not interpret. Under prompt injection that argument is exactly what an attacker rewrites, because it turns a plausible swap into a theft.
